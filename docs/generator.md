# The card generator

`README.md` in this repository is the GitHub profile. It is a thin hand-written
shell: every panel in it is an SVG under `cards/`, generated by
`cmd/gencards` and committed back by
[`.github/workflows/cards.yml`](../.github/workflows/cards.yml).

Do not edit anything under `cards/` by hand. It will be overwritten on the next
run, and CI fails if the committed cards do not match what the generator
produces.

## Why the panels are images

GitHub strips CSS from a README. There is no way to draw a bordered panel, a
bar chart or a two-column layout in markdown, so each panel is generated as one
SVG and placed with a `<picture>` block. That has consequences worth knowing
before changing anything:

- **Nothing inside a card can be a link.** To GitHub a card is one flat image,
  so a link has to wrap a whole image. That is why the six tiles under the
  header are six separate SVGs rather than one row: each needs its own `<a>`.
  Those tiles and the view counter are the only clickable or live things on
  the page.
- **A card cannot load anything.** GitHub renders it through an `<img>` tag,
  which blocks every external reference. Fonts, logos and cover art all have to
  be embedded in the file. That is why `internal/fonts` carries a woff2 and
  `internal/icons` carries path data instead of URLs.
- **Cards paint no background.** GitHub has four themes but `prefers-color-scheme`
  only reports light or dark, so Dark dimmed and Dark high contrast are
  indistinguishable from the default dark. Transparent cards let the real page
  colour through and read correctly on all four.
- **Text does not wrap or ellipsise.** SVG has no layout engine. `internal/svgx`
  computes every position from the font's own metrics, which is only practical
  because the whole design is set in one monospaced face where every glyph
  advances exactly 0.6em.
- **Declarative CSS does run.** Script never does, but keyframe animations
  work inside an `<img>`-loaded SVG, which is how the hand in the header waves.
  It honours `prefers-reduced-motion`.

## How the README spaces the panels

With no stylesheet, the gaps between the panels are whatever markdown's own
rules produce, and the two that hold the page square are both easy to undo by
accident.

**Every panel is wrapped in a `<p>`.** GitHub gives a paragraph a 16px bottom
margin and gives a bare `<picture>` nothing at all, so a panel written without
the wrapper sits about 6px from the next one while its neighbours sit 22px
apart. That wrapper is the whole of the page's vertical rhythm. The view
counter is the exception that needs nothing: a bare `<img>` on its own line is
already a paragraph.

**A row of two panels is written on one line with no space anywhere inside
it, and each half is placed at 50%.** Images are inline, so every newline or
space between the two `<picture>` tags — or between an `<img>` and its closing
`</picture>` — lays out as a real 4px space on the line. Two halves plus that
space overflow the row and the second one wraps onto a line of its own, which
is why the halves cannot simply be widened to 50% while the markup is written
across several lines. The gap between the two boxes is transparent padding
inside the images instead: `cards.RenderPair` renders each half into a document
a full `WidthFull/2` wide with `PairGutter` of empty space on the side facing
the other half. Two of them then tile the row exactly, and the row's right edge
lines up with every full-width card on the page.

## Layout

```
cmd/gencards        entry point: fetch, snapshot, render, stamp the README
counter/            the live view counter, deployed separately (see its README)
internal/sources    one file per API; each is allowed to fail
internal/model      the data the cards draw, and data/snapshot.json
internal/cards      one file per panel, laying out its own geometry
internal/svgx       SVG primitives and the text metrics the layout rests on
internal/theme      the dark and light palettes
internal/fonts      the embedded JetBrains Mono subset
internal/icons      vendored logo path data (generated, see below)
internal/linguist   language name to bar colour
internal/wordmark   prepares and reads the header artwork
tools/genwordmark   re-encodes that artwork into the committed assets/wordmark-*.png
```

The one piece of ornament is the flock: a single bird drawn seven times at
falling size and opacity across the top of the header, and three more beside
the number on the counter. It lives in `internal/cards/flock.go`, and is
duplicated in `counter/counter.php` because that file is deployed on its own.

## Failure is expected

Two of the sources — Wakapi and Kavita — run on hardware that is not always
up. Boxes get rebooted, certificates expire, tunnels drop. The workflow runs
unattended and commits what it produces, so an outage must not fail the run or
blank a card on a live profile page.

So every source writes into `data/snapshot.json`, which is committed alongside
the cards. When a fetch fails:

1. The error is logged as `kavita: ... (keeping the last snapshot)`.
2. That section of the snapshot is left exactly as it was, `fetched_at`
   included, so the age of the data stays visible.
3. Every card is still rendered. The one with stale data comes out
   byte-identical to the previous run.
4. The run exits successfully, and the workflow commits nothing for that card
   because nothing changed.

The other sources refresh as normal in the same run — one service being down
costs you that card's freshness and nothing else.

If a section goes more than a week without a successful refresh, the run logs
`WARNING: kavita last refreshed 30 days ago`. Failing soft is right; doing it
silently forever is not, and a stale card looks perfectly healthy on the page.

So **a card showing old numbers is a symptom, not a bug in the drawing code**.
Check the workflow log first, then `fetched_at` for that section in the
snapshot.

The run only fails outright if it cannot write its output.

One thing to check before blaming the code: the generator runs on a GitHub
Actions runner, which can only reach services exposed to the public internet.
If `KAVITA_URL` points at something only reachable on your LAN or through a
VPN, every run will fail that source no matter how the credentials are set.

## Configuration

Every source is optional. One with no credentials is skipped and its card
renders from the snapshot, so the profile stays intact while you set the rest
up.

### Secrets

| Secret | Used for | Notes |
| --- | --- | --- |
| `GITHUB_TOKEN` | the activity card | Supplied by Actions. Nothing to add. |
| `WAKAPI_URL` | the languages and coding-time cards | Base URL of your instance. |
| `WAKAPI_API_KEY` | the languages and coding-time cards | From your Wakapi profile settings. |
| `STEAM_API_KEY` | the Steam card | From <https://steamcommunity.com/dev/apikey>. |
| `STEAM_ID` | the Steam card | Optional. Without it the vanity name is resolved through the API. |
| `KAVITA_URL` | the Kavita card | Base URL of the instance, e.g. `https://kavita.example.com`. |
| `KAVITA_API_KEY` | the Kavita card | From the account's settings. The statistics endpoint is admin-only, so this has to be an admin account's key. |

The two self-hosted **URLs are secrets rather than variables, and have no
default in the code**. Repository variables are readable by anyone who can see
the repository, and the address of a machine you run is not something to
publish just to save a line of configuration. Neither hostname appears anywhere
in this repository; if a URL is unset, that source is skipped and its card
renders from the snapshot.

### Variables

| Variable | Default |
| --- | --- |
| `ANILIST_USER` | `Rabenherz` |
| `STEAM_VANITY` | `rabenherz` |
| `PROFILE_GITHUB_USER` | `Rabenherz112` |

These are public identities: they are on the cards, or in the README's links,
so a default in the code costs nothing.

AniList needs no credentials: it is a public GraphQL API and the profile is
public.

Steam's endpoints need the profile's **game details** set to public. When they
are private Steam answers with an empty list rather than an error, which the
generator reports as a failure so the card keeps its previous values instead of
rendering empty.

## Running it locally

Render from the committed snapshot, touching no network and needing no
credentials:

```bash
go run ./cmd/gencards -offline
```

Fetch whatever you have credentials for and rebuild:

```bash
WAKAPI_URL=https://wakapi.example.com WAKAPI_API_KEY=... go run ./cmd/gencards
```

Useful flags: `-out`, `-snapshot`, `-assets`, `-readme` (pass `-readme ""` to
leave the README's date line alone).

The date line itself is currently written **commented out**, so the page ends
at the view counter. `stampVisible` in `cmd/gencards/main.go` puts it back. It
is a constant rather than a deletion because the line lives between the
`generated:start` and `generated:end` markers and every run rewrites what is
between them: commenting the block out in the README would not survive the next
build, and cannot be done anyway, since the markers are HTML comments
themselves and HTML comments do not nest.

To see the cards as GitHub will render them, serve the repository over HTTP and
load the SVGs through `<img>` tags. Opening one directly is not a fair test: an
SVG opened as a document can reach the network, and one loaded as an image
cannot, which is the whole reason the font is embedded.

## Tests

```bash
go test ./...
```

Nothing reaches the network. Every source is tested against a stub HTTP server
returning trimmed copies of what the real API sends, so a change in field names
or nesting fails a test rather than quietly emptying a card weeks later.

The tests worth knowing about:

- `cmd/gencards`, `TestSelfHostedOutageKeepsTheCards` — runs the whole pipeline
  against stub APIs, takes Kavita away mid-test, and asserts the run still
  succeeds, the Kavita card comes out byte-identical to the previous one, the
  other sources still refresh, and the failure is logged. This is the
  self-hosted outage case, held in place.
- `cmd/gencards`, `TestUnconfiguredSourcesAreSkipped` and
  `TestFirstRunWithNoSnapshot` — a half-configured repository, and a fresh one
  with nothing reachable at all. Both still write all sixteen cards.
- `internal/sources` — for each API, the shape it expects plus the ways it goes
  wrong: a 500, a rejected key, an unreachable host, and the awkward ones that
  answer `200` with nothing useful. A private Steam profile and an empty Wakapi
  response both have to read as failures, because treating them as success
  would write zeroes into the snapshot and blank the card for good.
- `internal/svgx` — the text metrics the whole layout rests on, and a
  regression test for the coordinate rounding that once drew the Windows logo
  62% oversized.
- `internal/cards` — every card rendered in both palettes with hostile input
  (titles containing `&` and `<`, names too long to fit, a zero where a divisor
  goes) and parsed as XML. An unescaped ampersand from an API would otherwise
  ship a broken card.

CI runs those, plus a `gofmt` check, a scan for merge conflict markers, and one
smoke run of the real `gencards` binary into a temporary directory.

That last step used to regenerate every card and diff it against the committed
ones. It was dropped: the comparison only holds while every byte a card embeds
comes from a committed file, and it broke the day the runner's Go version moved
and the header card's PNG re-encoded differently for identical pixels. Rendering
is covered by the tests above, and the scheduled workflow rebuilds and commits
the cards daily, so a card left stale by a code change corrects itself within a
run rather than blocking the build.

## What the activity card shows

Seven verbs, and only seven: **opened, closed, merged, approved, changes,
released, joined**. They are the events where something reached a conclusion.

`joined` needs a note. It comes from GitHub's `MemberEvent`, which fires when a
collaborator is added to a repository — and GitHub makes the *actor* the person
who did the adding, not the person added. In a maintainer's own feed that one
event type therefore covers both "I was added here" and "I added someone to my
repo", which are not the same statement. Only the first belongs on the card, so
the converter checks that `payload.member` is the profile's own owner and drops
the rest.

Comments are excluded on purpose, in every form GitHub has them: issue
comments, commit comments, review comments, and reviews submitted as a plain
comment. They are the cheapest events to produce and the least informative to
read, and on a profile whose owner reviews heavily they would crowd out the
reviews themselves. `TestNoCommentsSurviveConversion` keeps any newly handled
event type from quietly reintroducing them, and `TestOnlyTheAgreedVerbs` pins
the set so adding a seventh has to be deliberate.

Pushes, forks, stars, wiki edits and repository creation are not shown either,
matching the `disabled_events` list in the previous profile's activity config.
The seven verbs above are exactly the event types that config left enabled.

## No data versus stale data

These are different states and the cards distinguish them.

- A section that has **never** fetched successfully draws an em dash. It is not
  drawn as zeroes, and it is emphatically not seeded with plausible-looking
  numbers: a source that has never worked must not be able to look like one
  that is working. This is what an unconfigured Kavita looks like.
- A section that fetched **before** but failed this time keeps its last values.
  That is the whole point of the snapshot, and after a week the run starts
  logging a warning about it.

`data/snapshot.json` ships empty for the same reason. A fresh clone renders
dashes until the first successful run, rather than a convincing set of numbers
nobody measured.

Which state a section is in is decided by its `fetched_at` and nothing else.
Filling in the figures by hand is not enough: a section left at
`"fetched_at": "0001-01-01T00:00:00Z"` is one that has never been fetched, and
its card draws dashes however complete the numbers beside it look. Hand-entered
values need a real timestamp of when they were read off the service, which also
puts them under the same staleness warning as everything else.

## Dependencies

The generator imports nothing outside the standard library, so `go.mod` has no
requirements and there is no `go.sum`. That is deliberate: this runs on a
schedule against a repository nobody looks at for months at a time, and the
best supply chain is the one that isn't there.

What does need watching:

- **GitHub Actions.** Pinned by major tag and tracked by
  [`.github/dependabot.yml`](../.github/dependabot.yml), weekly, grouped into
  one pull request.
- **The Go toolchain.** The workflows use `go-version: stable` rather than
  pinning to `go.mod`, so every run picks up the current patched toolchain.
  The `go` directive in `go.mod` states the language minimum, not the version
  CI uses.
- **The generated artefacts**, which no tool watches, because a card has to
  carry them rather than fetch them:
  - `assets/wordmark-dark.png` and `assets/wordmark-light.png` — the header
    artwork, re-encoded. Regenerate with `go run ./tools/genwordmark`.
  - `internal/fonts/JetBrainsMono-latin.woff2` — the Latin subset from Google
    Fonts. Replace the file to update it; nothing else needs to change unless
    the metrics move, in which case `internal/svgx` needs the new numbers.
  - `internal/icons/icons.go` — Simple Icons path data. Regenerate with
    `python tools/geniconsdata/main.py`.

## Changing things

**The cadence.** The schedule lives in `.github/workflows/cards.yml`. The cards
print it too, so change the `cadence` constant in `cmd/gencards/main.go` to
match. Hourly is what the original design called for; daily is what is set,
since it matches this repository's previous workflow and keeps the commit log
readable.

**How much each card holds.** The counts are at the top of
`cmd/gencards/main.go`: ten activity lines, five languages, a fourteen-day
chart, three series, three games. Raising one makes its card taller; nothing
else needs to change.

**Colours.** `internal/theme` holds both palettes. `internal/linguist` maps a
language to its bar colour; most are Linguist's own, but a few are the brand
colour instead because Linguist picks for a white page and values like
PowerShell's `#012456` vanish on a dark one.

**Logos.** `internal/icons/icons.go` is generated. To change the marks, edit
the lists in `tools/geniconsdata/main.py` and run it from the repository root.

The toolbox strip is the "Technologies & Tools" table from the previous profile
README and nothing else. Tools that are part of the infrastructure but were
never listed there belong in the prose above the strip, not in it. Five of the
listed tools have no mark to draw at all: Simple Icons dropped the Microsoft
ones over trademark policy, which rules out PowerShell, Command Prompt, VS
Code, Azure and Hyper-V.

```bash
python tools/geniconsdata/main.py
```

**The wordmark.** `assets/HeaderTransparent.png` is the source. It is
re-encoded as a paletted PNG, which halves it losslessly, and its near-white
greys are darkened for the light variant, because the artwork's tagline is
drawn for a dark background and would otherwise be invisible on white.

That re-encoding is **not** done at build time. `tools/genwordmark` writes
`assets/wordmark-dark.png` and `assets/wordmark-light.png` and both are
committed; the generator embeds them exactly as they are. Replace the source
artwork and you have to re-run the tool:

```bash
go run ./tools/genwordmark
```

The reason is worth knowing, because it is not obvious. `image/png`'s
compressor gives no guarantee that the same pixels encode to the same bytes on
a different Go release, and CI checks the committed cards against freshly
generated ones byte for byte. With the encoding happening on every run, the two
header cards changed the day the runner's toolchain moved from one Go version
to the next, with no change to the artwork, the code or the data. Committing
the encoded PNGs takes the compressor out of the build entirely.

`TestCommittedWordmarksMatchTheTool` catches the opposite mistake, of changing
the artwork or the folding and forgetting to re-run the tool. It compares
pixels rather than bytes, for the same reason.

If you replace the artwork with something that reads on both backgrounds, drop
the `WordmarkLight` flag from `theme.Light` and re-run the tool.

## Migrating from the previous setup

This replaces the `Readme-Workflows/recent-activity` action. When rolling it
out over the old profile repository, remove:

- `.github/workflows/set-activies.yml`
- `.github/recent-activity.config.yml`
- `assets/waving.gif` and `assets/placeholder-banner.png`, if nothing else uses
  them

The old workflow pointed `CONFIG_FILE` at `./.github/activity-config.yml`,
which does not exist in the repository; the config is at
`recent-activity.config.yml`. So it was running on defaults, or not working at
all.

The manga figures previously came from
`utility.theravenhub.com/scripts/github-pf-manga/`. The Kavita card reads the
same library directly. If you would rather keep that endpoint, replace the body
of `sources.FetchKavita`; nothing else needs to change.
